# 立绘单例：提示词与执行流程失效审计

日期：2026-09-28。范围仅为 `img_1.png`、用户强模式 `r1.png / r2.png`，以及已经生成的 illustration short/full。本文没有生成新图、运行新批次或修改正式技能默认。

## 结论

现有证据不支持“韩文翻译错了，所以图不好”的归因。核心语义、比例、倾斜方向、单图行为与背景规则基本忠实保留。失败主要发生在 **从参考到几何的设计转换** 和 **未校准就扩展的流程**：先决定大脸、眼坐标和路径，再把提示词保存为说明；没有证明同一输入下韩文、中文和调优提示词分别产生了什么差别。

立绘确实使用了自定义 Bézier paths，不是简单把 Moss 文件改个颜色；但“自定义路径”也不等于忠实造型。成图仍被统一的大凸面脸盘、接近的眼距／眼位和装饰贴片构图约束。身份线索被压缩成几个名词后，其连接位置、流向、薄厚与遮挡关系丢失。

主 Agent 转发的本轮用户原话为：

> 完全不接受，当前效果太差，我需要你将你的产物与我的aikon ref中的参考模式以及官方的参考图做像素级别的对比 找出你和它之间的差距 并弥补不足 关键点在于没有充分理解该类icon的特征，过于遵守原bot的绝对圆形头部，以及没有捕捉到相关ip的特征，没有还原，也没有将原始提示词翻译后的效果进行调优和对比就直接进行大面积测试 总体而言 当前是完全不合格的

用户最初明确要求充分理解源网页与提示词，并建立创建—测试—视觉验证—反馈—修正循环；保存未验收标签不能替代该循环中的单例校准。

## 翻译准确性与约束来源

| 源语义 | 当前译文／运行规则 | 判断 |
| --- | --- | --- |
| 短版大而圆的奶油脸、3:1 竖胶囊、15°、粉彩 | 均被保留 | 不是数字误译 |
| 完整版肤色／表面色、约 2.5–3:1、15–20° | 均被保留 | 不是数字误译 |
| `둥근`，并要求颊与下颌柔和连接 | 多处译成“大而圆／圆润”，优先序中用“圆形机器人脸” | 整体语义成立，但“圆形”可被过度几何化。应在生产层明确 rounded 不等于必须画数学圆或统一椭圆；不据此宣称整个译文失真 |
| 原发色、silhouette、约最多三项核心形态 | 译文保留 | “三项”不是删到三个标签；每项内部的走向和连接仍是身份信息 |
| 平滑大形、弱轮廓线、一档宽而弱的阴影、少量大高光 | 译文保留 | 不是零色阶、无前后层次，也不是控制点越少越好 |
| 源背景炭灰、单张输出 | 源译文保留；runtime 明确改为透明、每轮双版 | 是有记录的产品覆盖，不是翻译事故 |
| 双眼完整、整体一起倾斜、保留关键识别形态 | 译文保留 | helper 的比值合法不能证明三者在画面中共同成立 |

因此，两份正式源译文本轮不应为了迎合拒绝反馈而被随意重写。需要更正的是使用方式和可验证的设计合同。两份建议校准提示词仍注明源译改关系与 CC BY-NC 4.0，不冒称独立原创或已验证方案。

## r1 与 r2 不是完全一致的数值标尺

为避免只凭观感把“眼睛太细”写成事实，本轮对两个参考的明确眼区做了只读像素测量：区域内取 `max(R,G,B)<85` 的暗像素，以 PCA 主轴计算长／短方向投影范围。没有修改图片、重新渲染或生成候选。

| 图像 | 原图尺寸 | 左眼区域 `[x0,y0,x1,y1]` | 右眼区域 | 暗形主轴长宽比约值 |
| --- | --- | --- | --- | --- |
| r1 | 1280×1280 | `[100,600,320,930]` | `[520,780,750,1090]` | 左 1.96，右 1.94 |
| r2 | 1254×1254 | `[125,550,365,920]` | `[485,760,745,1100]` | 左 2.72，右 2.82 |

这是阈值和区域限定下的近似暗形测量，不是原作者矢量参数，也不是对示例的合格评分。区域内没有额外做连通域过滤；目视 ROI 主要覆盖单只眼，但仍需交叉核对。抗锯齿和边缘描绘会影响结果，但已足以发现 **r1 的宽眼型与源短版 3:1 存在实质区别**，r2 更接近完整版的范围。不能把两个参考说成严格同一眼形，也不能一面硬编码 3:1，一面保证复现 r1 的全部观感。

复算方法：暗像素坐标先减去均值，协方差为 `xx, yy, xy`，主轴方向取 `theta = 0.5 × atan2(2xy, xx−yy)`；分别投影到该轴及其垂线，取 `max−min+1` 得长短范围。已将完整 ROI 和方法发送独立 Agent 交叉核对。本文这一部分是眼部像素诊断，不声称已经完成用户要求的全图逐像素差距分析。全图比较还需分离 alpha／背景并对齐目标部位，不能直接拿不同角色、不同构图的原始 RGB 做一个整体误差值来代替风格与身份判断。

本次建议稿先保留各源 profile 的比例，先校准轮廓和相对布局。若用户随后要求优先接近 r1 的宽眼，应将 eye-ratio 作为独立试验和明确 profile 例外；不能悄悄改译文、伪造批准，或让 helper 的默认区间替用户决定审美目标。

## 生产提示词没有经过真正的效果对照

`create_drafts.py` 中，`FACE`、`HAIR_FRONT`、珊瑚束和 halo 都先以路径常量定义。`scene(profile)` 使用这些常量及固定眼坐标生成场景；`production_prompt(profile)` 另外读取中文源译文并拼接说明。helper 的 `render_scene` 只接受 scene 数据，既不读取图像也不解释生产 prompt。

这不意味着 Agent 完全没读提示词；实际已读取原文和参考。它意味着 **保存了一份 prompt 文档，不构成对该 prompt 绘制效果的试验**。当前 SVG 是 Agent 的一次手工几何解释，不能当作“中文提示词已调优”的证据，更不能据此评价韩文与中文哪个更有效。

| 已发生的过程 | 缺失的校准环节 |
| --- | --- |
| 实际看图，选三个身份名词 | 没有把分缝、主弧、束根、环的朝向与厚度画成可核对的关系说明 |
| 同一脚本生成路径和生产 prompt 文档 | 没有向独立绘制 Agent 只提供 prompt＋原始图像并检查其真实产物 |
| helper 成功输出、结构与 alpha 检查 | 没有先让同一 case 的风格和身份对照成为后续样例的门槛 |
| 将图标批量送统一渲染 | 在首个校准 case 未获反馈前扩展到了多个 IP／形态 |
| 保留 `unverified/pending` 等状态 | 状态诚实有必要，但没有防止未经确认的造型方法被批量复用 |

## 立绘单例的可见失真与可定位原因

### 1. 圆润被用成了共通的大脸布局

现有 illustration 两版的脸部路径完全相同，眼中心都是 `(98,374)/(270,374)`。两版只在眼宽高、角度、颜色及部分装饰色块上不同。其脸是自定义 path，并非 `<circle>`；因此不能指控为“真的只画了一个圆”。问题是先固定大凸面脸盘和眼布局，再把头发与饰件铺上去的构造方式。

内置 Moss、Relay、Lantern 的 full 示例均使用 `(115,352)/(280,352)`、`30×84` 双眼、17° 和同一 pivot。这些示范虽声明并非唯一模板，仍为 Agent 提供了很强的共同布局锚点。当前跨 IP 的相似感与此一致；是否由示例本身造成全部相似感，仍需隔离试验，不能仅凭相关性定论。

修改方向：保留圆润的视觉语法，让可见脸域、发际线、颊侧发束和裁切共同决定脸形及眼的位置。保留眼部几何关系，删除未经参考测定的绝对坐标指令。不要把“换一个复杂 path 字符串”当作摆脱模板的证明。

### 2. 身份压缩丢掉了形态关系

当前立绘仍能读到深灰发、珊瑚粉、青绿环三个色彩标签，但原图中珊瑚侧束的弯折／回卷、根部连接和前后遮挡，被更团状的花饰形状替代；右侧小束被概括为火焰式尖瓣。bob 的贴头体积和连续发流被几段长尖楔主导。选中正确颜色和部件名称不足以证明身份轮廓保真。

需要保留的是“特征＋关系”：主珊瑚束在头部左上外侧、次束在另一侧，分别如何与发根相接；深灰 bob 如何围绕脸颊收拢；halo 如何位于头部上方偏右且保持斜向薄环和透空。无法确认珊瑚区域到底是头发还是独立饰物时，保持材质未知；这不妨碍精确描述其可见轮廓。

### 3. halo 的方向与头部倾斜可能被重复编码

成图中的 halo 比原图更竖。脚本中的 halo 路径本身已沿斜向绘制，再随整个 head 旋转 15°／17°。如果设计时把原图的屏幕方向直接抄入局部路径，再叠加 head 旋转，最终方向就会偏离来源。

这是应核对坐标关系的具体风险，不是宣布所有附着件都不能随头旋转。正确关系是先区分 screen space 与 head-local space，再在最终渲染中检查 halo 相对头部和画面的长轴方向；不能仅检查 head 的数值合法。

### 4. “flat color”没有要求粗略曲线和贴纸式层次

不能说旧图完全没有阴影：短版有 11 条 path，完整版有 16 条 path，并含头发高光、阴影和珊瑚内瓣。问题是这些色面没有充分对应原图的体积转折和遮挡，局部像贴上的独立色块，曲线转接与收尖欠细致。

r1 还可见宽范围的柔和色调过渡；r2 主要依赖大片浅深色面和精细的曲线边界。两者都不等于粗轮廓加单一填色。源完整版允许有限的阴影与大高光；“保持极简”应限制无关细节，不能代替对主曲线的打磨。

helper 当前仅允许纯色绘制属性，不支持 `<defs>/<linearGradient>`。这是本地静态子集的设计限制，不是 SVG 格式或 code-first 方法天生不能表达柔和层次。本轮先用少量宽色阶校准，不修改 helper；如果后续证据表明必须使用平滑渐变，需单独讨论实现边界，不静默宣称当前子集已经完整复现 r1。

## 建议的提示词改动及理由

| 改动 | 理由 | 仍未证明的事 |
| --- | --- | --- |
| 生产提示词只保留已生效规则；源全文作为溯源链接 | 减少“黑底／单图”与覆盖规则同时出现的阅读负担 | 旧图已经是透明，不能把此次失败归咎于黑底冲突 |
| 删除固定脸范围、眼中心坐标及示例路径引用 | 这些值是第一次草绘选择，不是参考事实 | 删除后不保证新布局自动更好 |
| 将三条身份标签展开为轮廓、根部、流向、遮挡、相对位置 | 让输出可以逐项与原图核对 | 仍需要真实绘制和视觉比较 |
| 明确 rounded 是连续圆润曲率，不是固定圆模板 | 保留源语义，防止形式被绝对化 | 不支持恢复写实骨骼或原人类五官 |
| 强调宽色阶依附形体，主曲线平顺且收尖自然 | 防止将平涂误用成粗略贴片 | 不能靠增加 path 数证明层次改善 |
| 分开源 profile 比例与 r1/r2 的真实差异 | 防止量化规则掩盖审美冲突 | 当前仍未选定“更接近 r1 的眼”作为用户批准例外 |
| 在单例中逐项对照，暂停跨 IP 扩展 | 降低同一未校准解释被批量放大的风险 | 一例通过仍不证明跨模型或跨主体泛化 |

## 单例、单变量的对照计划

### L：先检验语言转换，而不是靠文件存在证明翻译有效

固定同一个 code-generating Agent／harness／模型版本、同一输入顺序（img1、r1、r2）、同一最小运行覆盖（透明、无水印、真实 SVG、当前 profile）和相同工具。若宿主提供 seed 或确定性设置，保持一致；未提供则记录未控制，不编造。

对每个 profile 分别比较：A 使用韩文原始源提示词；B 使用现有完整中文源译文。公共运行覆盖完全相同，不加旧坐标，不给旧 SVG／examples／本审计的失败诊断。唯一计划改变的文本因素是源规则语言。short/full 是两条独立实验线，不能把它们相互比较后称为语言效果。

由独立绘制 Agent 真正读 prompt＋图片并输出 scene/SVG，再用相同 helper 和 renderer 处理。记录实际 source hash、提示词、模型／工具、场景、SVG、预览和检查；盲化 A/B 标签给主 Agent 和用户对照。一次比较只能暴露明显偏差，不能估计统计成功率或保证跨模型等价。

主线程若先使用绘图模型测试两版提示词，可以将实际生成的 PNG 作为诊断参考，再做 SVG 校准；需单独记录其模型、输入与图像。PNG 不是 SVG 成品，图像提示词表现和后续代码重建表现也不能合并成一个“通过”。只运行 short/full 两版属于 profile 探索，并不是上面的韩文／中文语言单变量试验；不必为一次探索冒造因果结论。

### C：校准生产指令，每次只替换一个说明模块

L 完成后，固定选用的语言版本和全部其他规则。以旧生产提示词为基线，仅将“固定脸范围／眼坐标”段替换成建议稿中的“可见脸域与头发关系”段，作为一个**文本因子**。这不是声称最终几何只会变一个数值；绘制模型可能同时改变多个形状，必须报告实际 diff。

若这一变化改善可见脸域，再固定该候选，仅替换“身份标签”段为关系化身份描述；随后才固定几何、单独增加或调整一组宽色阶。每轮依然保留 short/full 两条 profile；比较对象是各 profile 的上一版本与当前版本，不是把同时变了颜色、比例、角度的 short/full 当作严格单变量实验。

### E：数值精调时使用真正的单参数对照

已有可接受的轮廓后，如果要核对眼睛粗细，只改变 `eyes.width`，冻结 `eyes.height`、眼中心、头部变换、所有轮廓和颜色；列出实际长宽比。若超出该 profile 的源区间，先记录待决例外并由主线程取得真实选择，再执行，不伪造 style override。

如果要核对裁切强度，只改变一个已命名的整体取景参数，保持主体内部相对几何不变；如果当前 helper 没有这个参数，不能把手工乱改多条路径称为单参数试验。需先定义可追溯的坐标变换，或如实将其记为多参数构图修改。

### 人类反馈门槛与停止条件

每个候选在同尺寸展示：原图头部、两个模式参考、候选的浅／深展示底及必要局部细节。原参考文件不改写。分开评价：风格贴近、身份轮廓、曲线／层次质量、几何禁项、修改范围。格式通过和 alpha 通过只回答技术项。

用户拒绝时，记录拒绝版本和明确原因，维持 draft，不增添新 IP，也不通过“换更复杂算法”绕过判断。连续两次同一修正没有可验证进展时，复查假设与对照设计。只有 img1 单例经用户实际反馈确认方向后，才扩大到第二个性质不同的主体；不能把用户选择存储目录当成风格验收。
